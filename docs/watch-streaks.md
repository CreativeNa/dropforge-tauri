# Анти-стрикосбиватель (Watch Streak Keeper)

Проектная записка: что нужно, чтобы поддерживать Watch Streak в DropForge.
Статус: **в работе: push-уведомления о старте стрима реализованы, модуль стриков — нет**.

## Задача

Отдельная вкладка в приложении, которая не даёт сбрасываться Watch Streak на каналах, где пользователь подписан и уже имеет серию: продлевать серию просмотром в тот день, когда она под угрозой сброса, и показывать, сколько баллов канала было до и стало после.

## Исследование API (19.11.2026)

Проверено на живом аккаунте, токен клиента `smartbox` (тот же, что у входа по коду устройства).

### Что работает

| Данные | Как получить | Проверка |
|---|---|---|
| Баллы канала | GQL `channel(name:"shroud"){ self { communityPoints { balance } } }` | вернул `1292` |
| Награда к получению | `communityPoints { availableClaim { ... } }` | поле есть |
| Кто в эфире | существующие запросы каталога/стримов | используется в фарме |
| **Watch Streak** | **PubSub-топик `viewer-milestones.<user_id>`** | подписка принята: `RESPONSE {"error":""}` |

### PubSub — главная находка

В веб-клиенте есть топик `viewer-milestones` с авторизацией `OAUTH` и события:

- `viewer-milestones-update` — обновление милестоунов,
- `watch-streak` — продление стрика,
- `streak-recovered` — восстановление стрика.

Подписка на `viewer-milestones.445439155` с нашим OAuth-токеном **работает**: сервер отвечает `RESPONSE` с пустой ошибкой и держит соединение. То есть события стрика можно получать в реальном времени — этим и надо пользоваться.

Формат payload события пока неизвестен: за 25 секунд простоя событий не было. Его надо поймать вживую (см. план).

### GQL по милестоунам — есть, но пустой

Найдено поле:

```graphql
query {
  channel(name: "shroud") {
    self {
      viewerMilestones { id value category channel { name } }
    }
  }
}
```

Поле существует (тип `ViewerMilestone`), но на всех проверенных каналах возвращает `null` — видимо, заполняется только когда милестоун активен/ожидает действия. Аргументов у поля нет (`category`, `first` не поддерживаются).

Интроспекция схемы у Twitch отключена, поля искались перебором.

### Список подписок

`currentUser.follows` существует, но сервер отвечает `service error` — у токена `scopes: null`. Эндпоинт `/oauth2/device` принимает параметр `scopes` (проверено: `user:read:follows` принимается), значит подписки можно включить повторным входом со скоупом.

### Ещё один канал данных

В чате Twitch есть сообщение `viewermilestone` с параметрами `msg-param-value` (число стрика) и `msg-param-copoReward` (сколько баллов начислено). Появляется, когда пользователь **сам делится** стриком — как источник не годится, но полезно для сверки.

## Проверка 23.11.2026: старт стрима через PubSub

Проверено на живом PubSub-соединении (с токеном и **без** токена — оба раза подписка принята):

| Топик | Что приходит | Проверка |
|---|---|---|
| `video-playback-by-id.<channel_id>` | `stream-up`, `stream-down` (при переходе), `viewcount` каждые ~30 с | живой канал 2thy (101041809) и satsuki_hotaru (676211287) отдают `viewcount`; офлайн-канал shroud (37402112) при подписке молчит |

Что это значит:

- **Опрос не нужен.** Достаточно один раз узнать состояние канала (Helix `/streams`) и дальше слушать PubSub: `stream-up` приходит в момент старта стрима, `stream-down` — в момент окончания.
- **Состояние при подписке не приходит.** Офлайн-канал ничего не присылает, живой — сразу `viewcount`. Поэтому на старте нужен один точечный запрос (seed), иначе неизвестно, идёт ли стрим прямо сейчас.
- **`viewcount` — не переход состояния.** Если считать его «концом стрима», состояние будет мигать; в коде он только подтверждает `live`.
- **Авторизация не обязательна** для этого топика (токен всё равно отправляем — на дропсы).
- Запасной путь — EventSub `stream.online` (WebSocket, нужен app access token): официальнее, но требует регистрации приложения и client secret.

### Реализовано в DropForge

- `pubsub-svc` принимает `--stream <channel_id>` (повторяемый) и подписывается на `video-playback-by-id.*`; сообщения отдаёт как `{"event":"stream","channel":..,"kind":"stream-up|stream-down|viewcount",..}`.
- Приложение читает `settings.streakChannels` (логины), один раз резолвит id через Helix и сеет состояние в `data/profile/streams.json`.
- Дальше состояние обновляется только событиями PubSub; на `stream-up`/`stream-down` пишется запись в журнал («Стрим начался: login» / «Стрим закончился: login»).
- Диагностика показывает `streak channels` и `stream: login — в эфире/офлайн (время)`.
- При перезапуске pubsub (сторож) состояние пере-сеивается одним запросом.

## Как отслеживать (предлагаемая схема)

1. **PubSub**: подписаться на `viewer-milestones.<user_id>` (расширить `pubsub-svc` вторым топиком), логировать все события в `data/profile/streaks.json`.
2. **Из события** брать: канал, число дней стрика, начисленные баллы, время. Это даёт точное «стрик продлён, теперь N дней, +M баллов» — ровно то, что нужно показывать.
3. **Пока событий не было** — держать собственную книгу: какие каналы сегодня смотрели и сколько минут.
4. **Продление**: если канал из списка в эфире и сегодня ещё не отмечен — смотреть 8–10 минут через `watcher-svc`.
5. **Баллы до/после**: `communityPoints.balance` до просмотра и после; событие `watch-streak` подтверждает, что прирост — именно стриковый бонус.

## Эксперимент 19.11.2026: просмотр не продлил стрик

Смотрели `streamdatabase` (стрик 6) через `watcher-svc` 12 минут:

- тиков: 12, сегменты скачивались, spade отвечал `204`;
- прогресс дропа на этом же канале шёл: `112 → 113` минут (то есть сервер наш просмотр для дропов засчитал);
- **стрик остался 6**, баллы канала не изменились (`44 509`).

Выводы, которые из этого следуют:

1. Просмотр через spade/HEAD-запросы сегментов засчитывается **для дропов**, но, похоже, **не засчитывается для баллов канала и стрика**.
2. Возможные причины: нужен реальный GET-плеер (а не HEAD), корректные поля `game`/`game_id` в spade-событии, либо стрик/баллы начисляются отдельным каналом телеметрии, которого у нас нет.
3. Значит, для стрик-модуля одного `watcher-svc` может не хватить: нужен «настоящий» просмотр (GET сегментов, корректный spade-payload), и это надо проверить отдельным экспериментом до реализации.

Что проверить в следующий раз:

- отправить spade с реальным `game_id`/`game` канала;
- качать сегменты GET-запросами (не HEAD) хотя бы раз в минуту;
- запросить claim баллов (`communityPoints { availableClaim }` → `claimCommunityPoints`) — возможно, баланс меняется только после явного клейма;
- сравнить поведение на канале, где стрик маленький (6), и где большой (281).
## Что осталось выяснить

1. **Формат payload** `viewer-milestones-update` / `watch-streak` — поймать живьём (нужно посмотреть канал, у которого стрик на грани, и дождаться события). Это закрывается включением логирования в `pubsub-svc` на один вечер.
2. **Граница суток** — в каком часовом поясе Twitch считает «сегодня». Выясняется практикой: посмотреть канал, проверить, в какой момент стрик засчитался.
3. **Нужен ли скоуп подписок** — если список каналов делаем вручную, не нужен; если автоматический — нужен повторный вход.

## Предлагаемая архитектура

- `data/profile/streaks.json` — по каналам: `login`, `live`, `streakDays`, `lastExtendedAt`, `watchedToday`, `pointsBefore`, `pointsAfter`, `lastEvent`.
- `streaks_snapshot` / `streaks_refresh` / `streaks_add` / `streaks_remove` / `streaks_kick` — команды Tauri.
- Планировщик: тик 5 минут, кандидаты — каналы из списка, в эфире, сегодня не смотрены; лимит N каналов в сутки, паузы, «тихие часы».
- UI: вкладка «Стрики» в том же стиле, таблица каналов, кнопка «Проверить сейчас», суммарные баллы.

## Ограничения

1. Один канал за раз.
2. Стрим должен быть в эфире.
3. Бюджет времени: 8–10 минут на канал.
4. Баллы растут и от обычного просмотра — «до/после» само по себе не доказывает продление, нужен событийный подтверждающий сигнал из PubSub.

## Риски

Автоматизация просмотра нарушает Twitch ToS. Последствия: от временной блокировки до постоянной, плюс возможное аннулирование баллов и наград. Для этой функции риск выше, чем у фарма дропов: там один стрим на игру, здесь — очередь каналов с одинаковой длительностью.

Меры снижения: 3–5 каналов в сутки, случайный разброс времени и длительности, паузы, только живые каналы, не круглосуточно, по умолчанию модуль выключен.

## План работ

1. ~~Разведка API~~ — выполнено: PubSub-канал найден, подписка работает.
2. **Поймать payload** события стрика (1 итерация, требует живого просмотра на канале со стриком).

6. Проверка на живом аккаунте: 1 канал, затем 3 канала (2–3 итерации).
